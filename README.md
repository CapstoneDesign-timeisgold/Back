# Jiki

**약속 참여 여부와 도착 상태에 따른 벌금과 보상 정산 서비스**

- 담당 역할: 백엔드, 팀장
- 기술: Java, Spring Boot, Spring Data JPA, Spring Security, MariaDB
- GitHub: [CapstoneDesign-timeisgold/Back](https://github.com/CapstoneDesign-timeisgold/Back)

## 시스템 구조

![지키 서비스 아키텍처](assets/jiki-architecture.png)

## 핵심 기능

- 약속 - 약속 생성 및 조회, 참여자 초대, 초대 수락과 거절, 참여 취소, 참여 마감 설정, 도착 상태 관리
- 정산 - 벌금과 보상 계산, 내부 잔액 반영, 정산 결과 및 거래 내역 조회
- 기타 - JWT 인증, 친구 요청과 수락 및 거절, 친구 목록 조회

## 문제 해결

### 1. 참여 상태 변경과 정산의 충돌 방지

#### 전체적인 아키텍처

[![참여 변경과 정산이 같은 약속 잠금을 사용하는 구조](assets/01-participation.png)](assets/01-participation.png)

#### 문제

- 참여 마감과 취소 기능 구현 중, 정산 대상 조회와 금액 반영 사이에 참여 상태가 바뀌면 정산 기준이 달라질 수 있는 구조 확인.
- 다른 요청의 처리를 기다린 뒤에도 잠금 대기 전에 읽은 참여 상태를 사용하면 최신 변경을 반영하지 못하는 문제.

#### 해결

- 정산 대상을 유지하려면 참여 변경과 정산을 순서대로 처리해야 한다고 판단해, 두 작업에 동일한 약속 행의 `PESSIMISTIC_WRITE` 잠금 적용.
- 잠금 대기 중 변경된 상태도 반영하도록, 약속을 먼저 잠근 뒤 참여 행을 잠금 조회해 최신 상태를 기준으로 처리.
- 마감 이후나 정산 완료 후 변경을 차단하고, 수락한 참여자만 정산 대상에 포함.

#### 결과

- 참여 변경과 정산의 처리 순서를 통일하고, 잠금 획득 후 최신 상태를 확인하는 구조로 변경.
- 마감 직전 변경 허용, 마감 정각부터 변경 차단, 정산 완료 후 도착 상태 변경 차단 검증.
- H2 JPA 테스트로 참여 상태와 마감 정보 저장, 첫 수락 이후 마감 변경 제한 확인.

### 2. 동시 정산 충돌과 금액 누락을 해결하고 재시도 정상 처리

#### 전체적인 아키텍처

[![약속 잠금과 계정 잠금 후 잔액과 거래 기록을 함께 저장하는 구조](assets/03-settlement.png)](assets/03-settlement.png)

#### 문제

- 약속별 잠금으로는 공유 계정의 갱신 순서를 통제하지 못해, 서로 다른 약속의 동시 정산 실험 20회 모두 데드락 발생.
- 계정 잠금 전에 읽은 잔액을 그대로 사용하면, 다른 정산이 반영한 최신 잔액을 놓칠 위험.
- 벌금 배분의 나머지 처리와 관리자 입금 기록이 누락되어, 전체 잔액 소실과 거래 내역 불일치 발생.
- 완료된 정산의 재요청에도 409를 반환해, 응답 유실 후 재시도를 정상 처리하지 못하는 문제.

#### 해결

- 같은 순서로 잠그면 교차 대기를 피할 수 있다고 판단해, 관리자까지 사용자 ID 순서로 계정 잠금 적용.
- 과거 잔액으로 계산하지 않도록, 잠금 획득 후 DB의 현재 잔액을 조회해 정산에 사용.
- 나머지를 관리자에게 적립하고, 잔액과 거래 내역, 확정 결과를 한 트랜잭션으로 저장해 금액과 기록을 함께 반영.
- 약속 ID로 확정 결과를 재사용해 재요청에 204를 반환하고, 금액 재반영과 중복 거래 기록 방지.

#### 결과

- 동시 정산 20회에서 데드락 실패 20회 → 0회로 감소하고, 추가 10회에서도 잔액과 거래 기록 일치 확인.
- 1,000원을 3명에게 각 333원씩 지급하고 관리자에게 1원을 적립해 전체 잔액 보존.
- k6 VU 10 재시도 300건의 204 응답 3건 → 300건으로 증가하고, 금액 반영은 약속별 1회 유지.
- 일반 테스트 82개 통과로 정산 동작과 오류 발생 시 전체 롤백 검증.

### 3. 약속 목록 N+1 개선으로 SQL 202회에서 2회로 감소

#### 전체적인 아키텍처

[![목록 조회에서 반복 SQL을 fetch join으로 줄인 구조](assets/02-query.png)](assets/02-query.png)

#### 문제

- 수락한 약속이 10개일 때 SQL 22회, 50개일 때 102회, 100개일 때 202회 실행되어 목록 크기에 따라 조회가 반복되는 문제 재현.
- 참여 정보 조회 후 지연 로딩된 약속과 생성자에 접근할 때마다 개별 SQL이 실행되는 원인 확인.
- 수락 상태를 애플리케이션에서 필터링해, 목록에 필요한 조건과 연관 데이터가 최초 DB 조회에 반영되지 않은 구조.

#### 해결

- 필요한 연관 데이터를 처음부터 함께 가져오면 반복 조회를 없앨 수 있다고 판단해, 약속과 생성자에 fetch join 적용.
- 수락한 약속만 DB에서 가져오도록 상태 조건을 조회 쿼리에 반영.
- 약속 10개, 50개, 100개에서 SQL 횟수가 일정한지 확인하는 회귀 테스트 추가.
- 동일 데이터로 k6 VU 1, 10, 30에서 개선 전후를 각 3회 측정하고 응답 데이터 검증.

#### 결과

- 약속 100개 조회 SQL이 202회 → 2회로 약 99% 감소하고, 10개와 50개에서도 2회로 유지되어 목록 크기에 따른 SQL 증가 해소.
- VU 10의 p95 응답 시간 3회 중앙값 58.09ms → 8.81ms, 84.8% 감소.
- 개선 전후 본 측정 82,405건에서 HTTP 오류와 응답 데이터 불일치 0건.
