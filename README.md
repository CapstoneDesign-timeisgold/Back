# Jiki

약속 참여 여부와 도착 상태에 따른 벌금과 보상 정산 서비스

- 담당 역할: 백엔드 개발, 팀장
- 기술: Java 17, Spring Boot, Spring Security, JWT, Spring Data JPA, MariaDB, AWS EC2
- GitHub: [CapstoneDesign-timeisgold/Back](https://github.com/CapstoneDesign-timeisgold/Back)

<br>

## 시스템 구조

## 핵심 기능

- 약속 - 약속 생성 및 조회, 참여자 초대, 초대 수락과 거절, 참여 취소, 참여 마감 설정, 도착 상태 관리
- 정산 - 벌금과 보상 계산, 내부 잔액 반영, 정산 결과 및 거래 내역 조회
- 기타 - JWT 인증, 친구 요청과 수락 및 거절, 친구 목록 조회

## 문제 해결

### 1. 참여 상태 변경과 정산의 충돌 방지

**문제**

참여 상태 변경과 정산을 각각 처리하면 정산 도중 대상이 바뀔 수 있었다. 또한 잠금을 기다리는 동안 다른 요청이 참여 상태를 변경해도, 대기 전에 읽은 상태를 기준으로 처리할 수 있는 구조였다.

**해결**

정산 대상을 일관되게 유지하려면 참여 변경과 정산이 같은 약속을 기준으로 순서대로 처리되어야 한다고 판단했다. 두 작업이 같은 약속 행의 `PESSIMISTIC_WRITE` 잠금을 사용하도록 변경했다.

참여 ID로 상태를 변경할 때도 약속 잠금을 얻은 뒤 참여 행을 잠금 조회하도록 했다. 이를 통해 대기 중 달라진 상태를 다시 확인하고, 참여 마감이나 정산 완료 여부에 따라 변경을 거절하도록 구성했다.

**결과**

같은 약속의 참여 변경과 정산을 순서대로 처리해, 정산 중 대상이 바뀌거나 이전 참여 상태로 요청을 처리하지 않도록 했다.

### 2. 약속 목록 조회의 반복 SQL 제거

**문제**

약속 목록을 가져온 뒤 지연 로딩된 약속과 생성자를 하나씩 조회하면서 SQL이 반복되는 문제가 있었다. 약속 수가 늘어날수록 조회 횟수도 함께 증가했고, 약속 100개를 조회할 때 서비스에서 실행한 SQL은 202회였다.

**해결**

목록에 필요한 약속과 생성자를 처음부터 함께 가져오면 개별 조회를 없앨 수 있다고 판단했다. 수락 상태를 DB 조회 조건에 넣고, 약속과 생성자는 fetch join으로 조회하도록 변경했다.

변경 후에는 약속 수가 늘어도 SQL 횟수가 일정한지 회귀 테스트로 확인하고, k6로 응답 시간을 비교했다.

**결과**

- 약속 100개 기준 서비스 SQL: 202회 → 2회, 약 99% 감소
- VU 10에서 p95 응답 시간의 3회 중앙값: 58.09ms → 8.81ms, 84.8% 감소
- 개선 전후 본 측정 82,405건에서 HTTP 오류와 응답 데이터 불일치 0건

로컬 환경에서 MariaDB와 k6를 실행하고, 조건별로 5초간 워밍업한 뒤 10초씩 3회 측정한 결과이므로, 운영 환경에서의 성능을 의미하지는 않는다.

측정 조건: [개선 기록](back/docs/IMPROVEMENT_LOG.md)

### 3. 정산 금액 보존과 동시 정산 처리

**문제**

벌금을 균등하게 나눈 뒤 남은 금액이 잔액에 반영되지 않는 문제가 있었다. 전원이 지각한 경우에는 관리자 잔액만 증가하고 입금 내역은 남지 않았다.

서로 다른 약속이 같은 사용자 계정을 동시에 정산하는 실험에서는 데드락으로 일부 정산이 실패했다. 이미 완료된 정산에 다시 요청했을 때도 정상 완료 여부를 확인하는 대신 409를 반환했다.

**해결**

금액이 빠짐없이 기록되려면 참여자에게 지급한 금액뿐 아니라 나머지 금액도 잔액과 거래 내역에 반영해야 한다고 판단했다. 나머지는 관리자에게 적립하고, 전원이 지각했을 때의 관리자 적립도 입금 내역으로 남겼다.

서로 다른 약속은 같은 계정을 사용할 수 있으므로 약속 단위 잠금만으로는 충분하지 않았다. 대상 계정을 사용자 ID 순서로 잠근 뒤 현재 잔액을 읽도록 변경했다. 잔액 변경과 거래 기록, 확정된 정산 결과는 하나의 트랜잭션으로 저장해 함께 반영되거나 취소되도록 했다.

완료된 정산의 재요청은 저장된 결과로 처리할 수 있다고 보고, 금액을 다시 계산하거나 반영하지 않고 정상 응답하도록 변경했다.

**결과**

- 1,000원을 3명에게 나눌 때 남는 1원이 관리자 잔액과 거래 내역에 반영
- 동시 정산 20회 실험에서 데드락으로 실패한 횟수: 20회 → 0회
- 개선 후 동시 정산의 잔액과 거래 기록이 기대값과 일치
- k6 VU 10으로 100회씩 3회 요청한 결과, 300건 모두 정상 응답하고 금액은 약속별 한 번만 반영
- 일반 테스트 82개 통과

동시 정산 실험은 로컬 MariaDB에서 두 요청이 충돌하도록 실행 시점을 맞춰 진행했다. 

실험 조건 및 검증 범위: [정산 검증 문서](back/docs/SETTLEMENT_INTEGRITY.md)

## 설계와 검증

### 첫 참여 수락 이후 마감 시각 변경 제한

약속과 참여자를 별도 엔티티로 나누고, 사용자별 참여 상태를 관리하도록 설계했다. 참여 마감은 현재 시각 이후부터 약속 시작 시각까지 설정할 수 있도록 제한했다.

현재 수락한 참여자만 확인하면 모두 취소한 뒤 마감을 다시 변경할 수 있다. 이를 막기 위해 첫 외부 참여자의 수락 여부를 별도로 저장하고, 이후 취소나 재초대가 발생해도 마감 변경 제한을 유지하도록 했다.

### 경계 조건과 실제 저장 결과 확인

마감 직전과 정각, 직후의 동작을 나누어 확인하고, 중복 초대와 권한 없는 요청, 정산 후 변경이 거절되는지 테스트했다.

MockMvc로 HTTP 응답을 확인하고 H2로 참여 상태와 마감 정보의 저장을 검증했다. DB 잠금이 필요한 동시 정산은 MariaDB에서, 반복 HTTP 요청은 k6로 확인했다.
