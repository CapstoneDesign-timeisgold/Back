# Jiki

**약속 참여 여부와 도착 상태에 따른 벌금·보상 정산 서비스**

**담당 역할**　백엔드 개발 · 팀장  
**기술**　Java 17, Spring Boot, Spring Security, JWT, Spring Data JPA, MariaDB, AWS EC2  
**GitHub**　[CapstoneDesign-timeisgold/Back](https://github.com/CapstoneDesign-timeisgold/Back)

![지키 서비스 아키텍처](jiki-architecture.png)

### 핵심 기능

**약속 관리** - 친구 요청, 약속 생성, 초대 수락·거절, 참여 취소를 지원한다. 참여 마감 이후에는 변경할 수 없으며, 수락한 참여자만 정산에 포함한다.

**정산** - 도착 상태에 따라 벌금과 보상을 계산해 잔액과 개인 거래 내역에 반영한다. 서비스 내부의 정산 시뮬레이션으로, 실제 결제는 처리하지 않는다.

JWT로 요청자를 식별한다. 약속 시작 이후 생성자만 정산할 수 있으며, 결과는 생성자와 수락한 참여자에게만 공개한다.

### 문제 해결

#### 1. 참여 상태 변경과 정산의 충돌 방지

- **문제:** 참여 상태 변경과 정산을 따로 처리하면 정산 도중 대상이 바뀌거나, 잠금을 기다리기 전에 읽은 상태로 변경을 처리할 수 있었다.
- **해결:** 참여 변경과 정산이 같은 약속 행의 `PESSIMISTIC_WRITE` 잠금을 사용하도록 했다. 참여 ID로 변경할 때는 약속을 잠근 뒤 참여 행도 잠금 조회해 최신 상태를 다시 확인한다.
- **결과:** 같은 약속의 변경과 정산을 순서대로 처리하도록 바꿨다. 참여 마감과 정산 완료 후에는 변경을 차단하며, 마감 전후의 수락·취소와 정산 후 변경 거절을 테스트했다.

#### 2. 약속 목록 조회의 반복 SQL 제거

- **문제:** 목록 조회 중 지연 로딩된 약속과 생성자를 하나씩 가져오면서 약속이 많아질수록 SQL 횟수와 응답 시간이 늘어났다.
- **해결:** 수락 상태 필터를 DB 조회 조건으로 옮기고 약속·생성자를 fetch join으로 함께 조회했다. SQL 횟수를 확인하는 회귀 테스트와 k6 부하 테스트를 추가했다.
- **결과:** 약속 100개 기준 서비스 SQL은 **202회 → 2회(약 99% 감소)**로 줄었다. VU 10에서 p95 응답 시간의 3회 중앙값은 **58.09ms → 8.81ms(84.8% 감소)**였고, 개선 전후 본 측정 82,405건에서 HTTP 오류와 응답 데이터 불일치가 없었다.

동일 PC의 MariaDB·k6에서 조건별로 5초간 워밍업한 뒤 10초씩 3회 측정했다. 운영 환경의 성능을 나타내는 수치는 아니다. 자세한 조건은 [개선 기록](back/docs/IMPROVEMENT_LOG.md)에서 확인할 수 있다.

#### 3. 정산 금액 보존과 동시 정산 처리

- **문제:** 벌금을 나누고 남은 금액이 사라지고, 전원이 지각했을 때 관리자에게 적립한 금액은 거래 내역에 남지 않았다. 서로 다른 약속이 같은 계정을 동시에 정산하면 데드락으로 일부 정산이 실패했으며, 완료된 정산에 다시 요청하면 409를 반환했다.
- **해결:** 나머지를 관리자에게 적립하고 입금 기록을 남겼다. 대상 계정을 사용자 ID 순서로 잠근 뒤 현재 잔액을 읽어, 잔액·거래 기록·확정 결과를 한 트랜잭션으로 저장했다. 반복 요청에는 금액을 다시 반영하지 않고 정상 응답하도록 변경했다.
- **결과:** 1,000원을 3명에게 나눌 때 남는 1원이 관리자에게 적립됐다. 동시 정산 20회 실험에서 데드락으로 실패한 횟수는 **20회 → 0회**로 줄었고, 잔액과 거래 기록도 일치했다. k6 VU 10으로 100회씩 3회 요청했을 때 **300건 모두 정상 응답하고 실제 정산은 약속별 한 번**만 반영됐다. 일반 테스트 82개도 통과했다.

로컬 MariaDB에서 두 정산이 충돌하도록 실행 시점을 맞춰 검증했다. 운영 환경의 실패율이나 처리량을 측정한 결과는 아니다. 실험 조건과 검증 범위는 [정산 검증 문서](back/docs/SETTLEMENT_INTEGRITY.md)에서 확인할 수 있다.

### 설계와 검증

- **참여 상태와 마감 정책:** 약속과 참여자를 분리해 사용자별 수락·거절·취소 상태를 관리한다. 참여 마감은 현재 시각 이후부터 약속 시작 시각까지 설정할 수 있다. 첫 외부 참여자 수락 여부를 별도로 저장해, 취소·재초대로 마감 변경 제한이 풀리지 않도록 했다.
- **경계 조건과 저장 결과 검증:** 마감 직전·정각·직후, 중복 초대, 권한 없는 요청, 정산 후 변경을 테스트했다. MockMvc로 HTTP 응답을, H2로 참여 상태와 마감 정보의 저장을 확인했다. 정산의 동시 처리와 반복 요청은 MariaDB·k6로 별도 검증했다.
