# 개선 및 트러블슈팅 기록

이 문서는 Jiki 백엔드를 개선하면서 발견한 문제, 해결 방식, 검증 결과를 기록한다. 기능 구현 목록과 별개로 보안·데이터 무결성·운영 관점의 개선 근거를 남기는 것이 목적이다.

## 1. JWT 기준의 사용자 식별과 리소스 권한 검증

### 문제

- 요청 본문의 `username` 또는 `creatorUsername` 값을 신뢰해 친구 요청과 약속 생성 주체를 정했다.
- 로그인만 했다면 다른 사람의 친구 요청을 수락/거절하거나, 관련 없는 약속의 정산 정보를 조회·실행할 가능성이 있었다.

### 해결

- JWT 인증 결과인 `Authentication.getName()`만 사용자 식별에 사용하도록 변경했다.
- 친구 요청 수락·거절은 요청을 받은 사용자만 가능하게 했다.
- 약속 정산 실행은 약속 생성자만, 정산 결과 조회는 생성자 또는 수락한 참여자만 가능하게 했다.

### 검증

- 컨트롤러와 서비스 단위 테스트로 다른 사용자의 요청 처리 및 정산 접근이 거절되는지 확인했다.

## 2. 애플리케이션 시작 실패: 순환 의존성 제거

### 문제

- `SecurityConfig`가 `UserSecurityService`를 주입받고, `UserSecurityService`는 `SecurityConfig` 안의 `PasswordEncoder` Bean을 필요로 했다.
- Spring Boot 3 환경에서 순환 의존성이 허용되지 않아 서버가 시작되지 않았다.

### 해결

- `PasswordEncoder` Bean을 `PasswordConfig`로 분리해 보안 설정과 사용자 인증 서비스의 결합을 끊었다.

### 검증

- Oracle JDK 17과 MariaDB 환경에서 Spring Boot가 8080 포트로 정상 기동되는 것을 확인했다.

## 3. 정산 대상·시점의 데이터 무결성

### 문제

- 초대를 수락하지 않은 `PENDING`, 거절한 `DECLINED` 사용자까지 벌금·보상 계산에 포함됐다.
- 약속 시각 전에도 정산을 실행할 수 있었다.

### 해결

- `ACCEPTED` 참여자만 정산 결과와 벌금·보상 계산에 포함하도록 제한했다.
- 약속의 날짜와 시간을 확인해 예정 시각 전 정산을 차단했다.
- 미정산 결과 조회, 중복 정산, 예정 시각 전 정산은 인증 오류가 아닌 `409 Conflict`로 응답하도록 `ConflictException`을 도입했다.

### 검증

- 수락/대기/거절 참여자가 섞인 정산 결과에서 수락한 참여자만 포함되는지 테스트했다.
- 미래 약속의 정산 실행이 거절되는지 테스트했다.

## 4. 친구 요청과 약속 초대 중복 방지

### 문제

- 자기 자신에게 친구 요청 또는 약속 초대를 보낼 수 있었다.
- 이미 대기 중이거나 수락된 친구 관계를 다시 생성할 수 있었다.
- 같은 약속에 같은 사용자를 여러 번 초대할 수 있었다.

### 해결

- 자기 자신을 대상으로 한 요청을 차단했다.
- 양방향 친구 관계에서 `PENDING`, `ACCEPTED` 상태가 있으면 중복 요청을 `409 Conflict`로 거절했다.
- 참여자 테이블에 `promise_id + guest_id` 고유 제약을 추가했다.
- 거절된 약속 초대는 새 행을 만들지 않고 기존 초대를 다시 `PENDING`으로 전환하도록 했다.

### 검증

- 자기 자신 요청과 대기 중인 중복 초대가 거절되는지 단위 테스트로 확인했다.

## 5. 약속 생성 입력값 검증

### 문제

- 빈 제목, 음수 벌금, 범위를 벗어난 좌표, 잘못된 날짜·시간이 저장될 수 있었다.
- 형식만 그럴듯한 존재하지 않는 날짜도 이후 정산 단계까지 남을 수 있었다.

### 해결

- 약속 생성 요청에 Bean Validation을 적용했다.
  - 날짜: `yyyy-MM-dd` 형식
  - 시간: `HH:mm` 형식
  - 제목: 필수, 100자 이하
  - 벌금: 0 이상
  - 위도: -90~90, 경도: -180~180
- 서비스 계층에서도 날짜·시간을 실제로 파싱해 `2026-02-30` 같은 존재하지 않는 날짜를 DB 저장 전에 차단했다.

### 검증

- 잘못된 필드가 Bean Validation에 의해 감지되는지 확인했다.
- 존재하지 않는 날짜 요청이 Repository 호출 전에 거절되는지 확인했다.

## 6. 약속별 참여 마감과 취소

- 생성자가 참여 마감을 정하도록 `participationDeadline`을 추가했다. 현재 시각 이후, 약속 시작 이하의 시각만 허용한다.
- 마감 전 초대·수락·거절·참여 취소를 허용하고 마감 정각부터 변경과 약속 삭제를 차단한다.
- 첫 외부 참여자 수락 이후에는 마감 변경을 영구 제한한다. 취소·재초대로 해제되지 않도록 별도 플래그를 저장한다.
- 정산 이후 도착 상태 변경을 차단하고, 참여 변경과 정산이 같은 약속 잠금을 사용하도록 했다.
- 상세 응답에 참여 ID·사용자·상태를 묶은 목록을 제공한다.
- API, 기존 데이터 처리, 배포 SQL과 검증 범위는 [참여 마감 문서](PARTICIPATION_DEADLINE.md)에 정리했다.

## 7. 약속 목록 N+1 개선과 k6 실측

- **문제:** 약속 목록에서 지연 로딩된 약속·생성자를 개별 조회해, 수락 약속 10/50/100개에 대한 서비스 SQL이 각각 22/102/202회로 증가했다.
- **변경:** 수락 상태를 DB 조건으로 옮기고 약속·생성자를 fetch join했다. 서비스 SQL은 모든 조건에서 2회로 줄었다.
- **측정:** 약속 100개·k6 VU 10 조건에서 p95 응답 시간의 3회 중앙값이 **58.09ms → 8.81ms(84.8% 감소)**였다. 이는 위 조회 변경의 효과를 측정한 것으로, 별도의 추가 최적화 결과가 아니다.
- **검증:** VU 1/10/30의 전후 본 측정 총 82,405건에서 HTTP 오류와 응답 필드 불일치 0건. 일반 테스트 70개 통과. 목록 크기가 늘어도 SQL 2회를 유지하는 회귀 테스트를 추가했다.
- **조건과 한계:** 동일 PC의 MariaDB 10.11.19·k6 2.3.0, 워밍업 5초 후 조건별 10초 × 3회. 같은 계정과 생성자가 모두 다른 테스트 데이터를 사용한 짧은 로컬 실험이며 운영 성능을 뜻하지 않는다.

## 테스트 실행

Git Bash에서 다음 명령으로 전체 단위 테스트를 실행한다.

```bash
./gradlew.bat test
```

성능 테스트는 일반 테스트에서 제외하며, Java 17·k6와 별도 로컬 `jiki_perf_*` MariaDB 스키마를 준비한 뒤 실행한다. DB 계정은 `PERF_DB_USER`, `PERF_DB_PASSWORD` 환경 변수로 전달한다.

```powershell
./docs/performance/run.ps1 -Label after-check -JavaHome $env:JAVA_HOME -K6Path (Get-Command k6).Source -Database jiki_perf_check -DatabasePort 3306
```

성능 테스트는 전용 DB의 엔티티 테이블을 생성·삭제하므로 빈 실험용 스키마를 사용한다. 생성되는 상세 보고서와 원본 결과는 로컬에만 보관한다.

## 남은 개선 과제

- `admin` 사용자명 하드코딩을 역할(Role) 또는 별도 정책으로 분리
- 배포 환경에서 CORS 허용 출처를 프론트엔드 도메인으로 제한
- 예상치 못한 예외의 상세 메시지를 API 응답에서 제거하고 서버 로그로 관리
- MariaDB를 포함한 회원가입 → 친구 → 약속 → 정산 전체 통합 테스트 추가
